Real Data Ingestion from Public APIs

Three public data sources power the system

Solar Data: pvlib Integration

☀️ NREL PVGIS Historical Weather Data

Data provided:

  • Solar irradiance (direct, diffuse, global horizontal)
  • Air temperature & humidity
  • Azimuth & zenith angles for PV tracking

How it works:

User places source on map → captures lat/lon → pvlib fetches real historical weather for that location → generates realistic 30-day solar production curves

Wind Data: windpowerlib Integration

💨 ERA5 Reanalysis Weather Data

Data provided:

  • Wind speed at hub height (10m, 100m)
  • Wind direction & surface roughness
  • Temperature & pressure profiles

How it works:

Coordinates + standard turbine model parameters → windpowerlib calculates power curves → 30-day realistic wind profiles

Market Data: NYISO/PJM APIs

💡 Real-Time Electricity Market Prices

Data provided:

  • Day-ahead LMP (Locational Marginal Pricing)
  • Real-time pricing updates
  • Generation costs & reserve prices

How it works:

Market prices drive optimization: when prices are low → charge battery; when prices are high → discharge battery or sell to grid

Data Ingestion Pipeline

db-init Service (runs once at startup):

  1. Reads user-placed source coordinates from map
  2. Calls pvlib API with lat/lon → fetches solar data
  3. Calls windpowerlib API with lat/lon → fetches wind data
  4. Calls NYISO/PJM API → fetches real market prices
  5. Generates synthetic 30-day profiles matching real data
  6. Streams to Kafka topics at 5-minute intervals

Microservices Architecture

Independent services communicating via REST & Kafka

Always-Running Services

🔧 Backend (FastAPI)

REST API server on port 8000

Serves historical/forecast data, runs PuLP optimization, manages battery state

⚛️ Frontend (React)

Interactive map on port 3000

Click-to-place sources, real-time dashboards, optimization visualizations

📡 Consumer (Kafka)

Listens to 4 topics

Persists solar, wind, load, market streams to TimescaleDB

🗄️ TimescaleDB

Time-series database

Hypertables auto-partitioned by time, compressed storage

🎥 Kafka & Zookeeper

Message broker

Topics: solar, wind, load, market (5-min intervals)

📊 MLflow

Model registry

Tracks models, versions, artifacts, metrics

On-Demand Services (Profile: task)

🤖 Training Pipeline

Runs time-series cross-validation on accumulated historical data

Tests 5 models: Random Forest, ARIMA, Prophet, MLP (PyTorch), Temporal Fusion Transformer

Registers best model per dataset-source pair in MLflow Registry

🔮 Inference Pipeline

Loads trained models from MLflow

Generates 30 steps ahead (150 minutes) with 5-min resolution

Writes forecasts (yhat) + confidence intervals to forecast hypertables

End-to-End Data Flow

From user action to optimized dispatch

Step-by-Step Journey

  1. 1. User places source on map (captures coordinates)
  2. 2. db-init fetches real API data using exact coordinates
  3. 3. Synthetic profiles generated (30-day realistic curves)
  4. 4. Kafka producers stream to 4 topics at 5-min intervals
  5. 5. Consumer ingests & persists to TimescaleDB (compressed, partitioned)
  6. 6. Training pipeline runs CV on accumulated data, compares models
  7. 7. Best models registered in MLflow with version tracking
  8. 8. Inference generates forecasts (30 steps, 5-min resolution)
  9. 9. Backend solves optimization problem for battery dispatch
  10. 10. Frontend displays historical + forecasted data & recommendations

Key Implementation Details

Database, Optimization & ML Specifics

TimescaleDB Schema

Data Tables (Hypertables):

  • solar, wind — with source_id (multiple generators)
  • load, market — no source_id (single aggregate)
  • Columns: timestamp (partitioned), value, metadata

Forecast Tables:

  • solar_forecast, wind_forecast, etc.
  • Stores yhat (predicted value) + confidence intervals

Battery Table:

  • battery_state — SOC, charge_rate, discharge_rate per battery_id

Optimization: PuLP Linear Programming

Objective (minimize cost):

Σt price[t] × (grid_buy[t] - grid_sell[t])

Subject to constraints:

  • SOC Dynamics: SOC(t) = SOC(t-1) + η×Charge(t) - Discharge(t)
  • Grid Balance: solar + wind + Charge - Discharge = load + grid_sell
  • Buy/Sell Exclusive: Big-M formulation with binary variable
  • Battery Limits: Min/max SOC, max charge/discharge rate

ML Pipeline: Model Training & Registry

Models Tested:

  • Random Forest (scikit-learn)
  • ARIMA (auto d parameter)
  • Prophet (Facebook)
  • MLP (PyTorch neural network)
  • Temporal Fusion Transformer (deep learning)

Validation Strategy:

  • Time-series cross-validation (anchored forward chaining)
  • Metric: MSE (Mean Squared Error)

MLflow Registry:

  • Model names: Best_solar_010780_Model, Best_load_Model
  • Artifacts: Pickle files (not native sklearn logging)

Deployment & Docker Profiles

Startup Sequence

1. Start infrastructure:

docker-compose up -d timescaledb zookeeper kafka mlflow

2. Start consumer:

docker-compose up -d consumer

3. Initialize & stream data:

docker-compose --profile init up db-init

4. Start application:

docker-compose up -d backend frontend
